# Архітектура — огляд

rombik побудований як **конвеєр компілятора**: фронтенд (парсер) → проміжне
представлення → бекенд (рендер). Кожен крок — окремий Go-пакет з єдиною
відповідальністю та мінімумом залежностей.

## Пакети й залежності

```
   cmd/rombik (CLI) ─┐
   cmd/wasm (легкий) ─┤  адаптери входу/виходу
   cmd/wasmraster ────┤
   pkg/rombik (фасад) ┘
                                       │
   parser/python ──► AST-JSON ──► parser/astjson ──► ir
   (python3 + ast)   (рядок)        (FromJSON)        │
                                                      ▼
                                                   layout ──► diagram ──┬─► render/svg
                                                   (Build)              ├─► render/typst
                                                      │                 └─► render/raster (PNG/PDF)
                                                      └─ використовує route (A*)
```

Стрілки — напрям залежності (хто кого імпортує). Ключове:

- **`ir`, `diagram` — листя.** Майже ні від чого не залежать (лише stdlib). Чисті
  моделі даних. → [[IR-проміжне-представлення]], [[Diagram-модель-геометрії]].
- **`layout` залежить лише від `ir`, `diagram`, `route`.** Не знає ні про Python,
  ні про формат виводу, ні про ОС. → [[Layout-рушій-розкладки]].
- **Три рендери, кожен залежить лише від `diagram`.** `render/svg` і `render/typst` —
  на stdlib; `render/raster` (PNG/PDF) — на `tdewolff/canvas`. → [[SVG-рендерер]],
  [[Typst-рендер]], [[Растровий-рендер-PNG-PDF]].
- **`parser/astjson` залежить лише від `ir`.** Спільний для всіх мов/середовищ.
- **`parser/python` — єдиний, хто торкається ОС** (`os/exec` → `python3`). Тому його
  **не імпортує** жодна WASM-збірка. → [[Розділення-відповідальностей]].
- **`pkg/rombik`** — необов'язковий фасад над усім цим для бібліотечного вжитку. →
  [[Публічний-API-rombik]].

## Ядро vs адаптери

| Шар | Пакети | Властивість |
|-----|--------|-------------|
| **Ядро** | `ir`, `layout`, `diagram`, `render/{svg,typst,raster}`, `route`, `parser/astjson` | Без ОС/мережі/мови. Однаково в CLI і WASM. |
| **Адаптери входу** | `parser/python` (CLI), Tree-sitter (браузер) | Дають AST-JSON. Залежать від середовища. |
| **Адаптери виводу** | `cmd/rombik` (файли), `cmd/wasm`+`cmd/wasmraster` (JS), фронтенд | Серіалізують результат. |
| **Фасад** | `pkg/rombik` | Необов'язкова склейка для бібліотек. |

Межа між ядром і адаптерами — **AST-JSON на вході** і **Diagram → SVG/Typst/PNG/PDF/JSON
на виході**. Усе посередині не знає, звідки прийшли дані й куди підуть. →
[[Чому-AST-JSON-як-контракт]].

## Потік даних

Детально по кроках — у [[Конвеєр-обробки]]. Стисло:

1. **Код → AST-JSON.** `parser/python` запускає `parser.py` через `python3`
   (у браузері — Tree-sitter). → [[Парсер-Python]].
2. **AST-JSON → IR.** `astjson.FromJSON` будує дерево `ir.Func`/`ir.Block`/`ir.Node`.
3. **IR → Diagram.** `layout.Build` рекурсивно рахує габарити (`size`) і роздає
   координати (`place`). → [[Розкладка-рекурсією-size-і-place]].
4. **Diagram → вихід.** `svg.Render` (SVG), `typst.Render` (Typst/CeTZ), `raster.PNG`/
   `raster.PDF` (нативні PNG/PDF), або `json.Marshal` (геометрія). Усе — без зовнішніх
   бінарників.

## Чому такі межі

- **Тестованість.** Ядро можна годувати IR напряму, без Python.
- **Багатомовність.** Новий фронтенд (C++, JS) лише має видати AST-JSON — решта
  безкоштовна. → [[Як-додати-нову-мову]].
- **WASM.** Та сама межа дозволяє викинути `os/exec` із браузерної збірки і
  отримати нуль-серверний застосунок. → [[Браузерний-рушій]].
